# Design

## Context

动机与已确认范围见 `proposal.md`。本次跨来源适配、入库事务、页面验收与存量数据迁移，需要在实施前明确设计。

当前实现已分层：`etl/sources.py` 声明并读取来源，`etl/transforms.py` 清洗，`etl/repository.py` 负责事务，`etl/run_etl.py` 编排。CSV 当前只做列重命名；公共薪资解析器会把无单位数值当成千元，不能直接接受新文件的元/月数值。

`replace_snapshot()` 当前只覆盖同一标签；移除 2021 必须扩展事务边界。页面从数据库读取期次，未知标签回退最新登记快照；无技能页已有空态。测试已使用 `tests/support.py` 的独立 MySQL 测试库，现有常规样例仍是 2018 与 2021。

探索阶段已在内存读取公开文件：28,162 行，12 城市，10 个搜索类别；学历空值 105 条、经验空值 49 条，按去除首尾空白后的岗位/公司/城市组合估算约 24,840 个组合。该估算不直接作为最终 ETL 金样例，正式基线必须由项目实际清洗规则生成。

## Goals / Non-Goals

**Goals:**

- 给数值月薪增加来源层适配，继续复用公共文本薪资解析、枚举归一和快照内去重。
- 在一个数据事务内完成 2020 写入与 2021 移除；普通重导保持已有隔离保证。
- 让当前期次、页脚、城市选项和技能空态与实际数据一致，具备失败回滚及可重现验收路径。

**Non-Goals:**

- 不获取或虚构 2024 数据，不声明完整年度或全国覆盖，不增加实时爬虫。
- 不补造技能、从岗位类别推断技能，或解析混合公司标签以扩展公司规模/行业图表。
- 不重构账号、验证码、图表布局或现有表结构，不引入新依赖，不实现跨期趋势比较。

## Decisions

### D1：固定来源版本，保留“公开快照”的时间含义

- 来源仓库：https://github.com/ccclll777/bosszp
- 文件：`job_data_clean_price.csv`
- 固定提交：`2dcc08a8ff0c79a0afda3d150c1a9618ebe6e390`，文件提交时间为 2020-04-21。
- 获取地址：https://raw.githubusercontent.com/ccclll777/bosszp/2dcc08a8ff0c79a0afda3d150c1a9618ebe6e390/job_data_clean_price.csv
- 本地保存：`data/raw/bosszp_2020_job_data_clean_price.csv`，沿用 `data/raw/` 不入 Git 的约定；获取时记录原始文件 SHA-256 与完整性核验结果到数据说明。
- `period` 使用“2020 年 4 月公开快照”，`note` 写明 12 城市 IT 岗位样本、无逐条发布日期和无技能明细。

固定提交优于直接跟随 `master`，能够重现同一数据版本。上传时间和作者同期说明可以说明公开快照的时间背景，但不能证明每条招聘的实际发布日期，因此不增加伪造的岗位日期字段。

### D2：在来源适配层构造带单位薪资

为 CSV 配置增加可选 `salary_columns`，描述原始最低、最高月薪字段；没有该配置的 CSV 沿用现有文本薪资读取。适配前检查原始上下限字段是否存在，缺列报出原字段名称。

2020 字段映射如下：

| 统一字段 | 来源字段或处理 |
| --- | --- |
| `title` | `job_title` |
| `company` | `job_company` |
| `city` | `company_city` |
| `education` | `job_education` |
| `experience` | `job_experience` |
| `salary` | `job_low_salary` 与 `job_high_salary` 转成明确的元单位区间 |
| `key_word` | `job_type`，仅保留搜索上下文，不作为技能 |

上下限用数值转换处理；两端均为有限、非负数且下限不大于上限时，构造类似 `8000元-13000元` 的文本，交给现有清洗流程计算中点。无效数值整条薪资置缺失，不能只保留一端让公共解析器误当单一值。公共解析器仍保留裸数按 k 的原规则，避免改变 2018 数据解释。

不直接采用 `job_ave_salary` 作为权威均值，保证所有来源均按上下限中点计算。缺失学历、经验保留为空；来源已经预处理，缺少原始带薪月数时不额外猜测或折算。`job_company_tag` 为混合标签，本次不拆解。

### D3：替代关系由快照声明控制，沿用原有命令

在 2020 快照配置中声明 `replaces: "2021"`，移除常规 2021 导入配置；运行入口仍为 `python -m etl.run_etl --snapshot 2020`，不额外增加用户输入任意待删标签的命令行参数。

`run_snapshot()` 完成读取、校验、清洗并确认岗位非空后，将受控替代标签传给入库层。无替代声明时仍为普通批内覆盖。只允许本变更配置中的 2020→2021 关系，拒绝同标签替代、移除 2018 或其他未经声明的标签；重复执行时旧标签不存在属于正常状态。

该方式让成功导入和旧样本退出保持一致，避免只删除配置却把旧数据留在期次下拉里。先删旧数据再导入的做法被否：来源或写入失败会使现有样本不可用。

### D4：新旧快照数据变更一起提交

事务内依次完成：注册/更新 2020 元数据、覆盖本期岗位与技能、删除 2021 的岗位与技能、删除 2021 元数据，最后统一提交。任一步失败则统一回滚。

只有这些数据操作进入替换事务；现有建表入口仍在之前执行，不把可能隐式提交的 DDL 混入替换事务。移除旧快照按标签解析到实际 id，再按 id 定位派生记录，不依赖标签等于自增 id。不得触碰 2018、`users`、`captcha_challenges` 或原始暂存表。

不复用 2021 的 id 并直接改标签：独立登记 2020 更易追溯来源，也避免旧新样本在中途被混作同一期。

### D5：复用页面与默认期次机制，更新样例期次

迁移前库中已有 2018；新增 2020 后其登记 id 更大，移除 2021 后现有“最新登记”解析会默认选择 2020。全新安装文档继续按年份顺序导入 2018，再导入 2020。重导 2018 更新已有元数据，不新增登记，因此默认期次保持 2020。

不扩大为任意乱序历史快照的排序机制重构；交付时必须验收当前库和文档所述新安装路径均默认 2020。若实际存量元数据与该前提冲突，应在 apply 阶段报告，不能静默改写无关期次或放宽默认展示要求。

`snapshot=2021` 沿用未知标签回退，并验证选中项与页脚为实际 2020。2020 技能查询为空，2018 技能照常显示。普通测试样例改为 2018/2020；专门的替换测试额外构造 2021，不把真实大文件行数写进页面测试。

### D6：以小样例验证规则，以固定来源核验数据质量

- 单元测试用临时小 CSV 覆盖数值单位、缺列、无效区间、学历经验缺失和文本来源兼容。
- 独立 MySQL 测试库验证新写入和旧移除的原子性，包括“移除旧数据后故障”的回滚，已有 2020 的再次替换失败，以及 2021 不存在时的重复执行。
- 页面回归验证默认期次、旧链接、跨页筛选、12 城市来源说明和技能空态；常规样例不依赖外部完整文件。
- 实际文件质量核验记录原始/去重后条数、薪资有效与缺失数、学历经验异常取值、12 城市及地图映射覆盖。约 2.48 万是预估，不绕过实际清洗结果固化它。

## Risks / Trade-offs

- [文件名中的 clean 表明源文件已预处理，无法恢复未公开的原始记录] → 说明来源层级，保留固定版本与校验值，不声称覆盖完整招聘市场。
- [元数值被默认 k 解析而放大薪资] → 来源层显式补元单位，使用 8000/13000→10500 的回归用例。
- [无效数值被公共解析器部分接受] → 数值适配阶段校验完整区间，任何一端无效则整组缺失。
- [被移除的 2021 仍有技能或元数据残留] → 三表一起按旧快照 id 移除，集成测试断言不存在残留。
- [样本重复键与公共清洗的空白归一规则不同] → 正式下载后用项目流程重新建立准确基线，不为凑齐预估条数修改去重规则。
- [12 城市覆盖与 2018 期采样方式不同] → 按期隔离、标清覆盖范围，不新增跨期涨跌结论。
- [无技能数据] → 沿用已确认的降级提示，不伪造技能。

## Migration Plan

1. 获取固定版本 CSV 并核验；完成来源适配与独立测试库的全量回归。
2. 对实际业务库记录 2018 岗位、技能和元数据基线及账号数量，并对 2021 三表相关记录按快照范围导出可恢复备份；保留原有 2021 CSV 和旧配置的版本记录。
3. 在实际库运行 2020 ETL；清洗和数据质量检查成功后，由上述事务一起替换 2021。
4. 检查快照标签为 2018/2020，2018 基线与账号不变，2021 无三表残留；再重导一次 2020 验证幂等。
5. 验证五页、2018 技能页、2020 技能空态、旧 2021 URL 与页脚。将准确条数和薪资口径写回数据文档。
6. 回滚：先恢复本次实施前的代码与来源配置；使用保存的 2021 派生记录及元数据备份，在受控事务中恢复 2021 并按标签清理新导入的 2020，核验默认期次和 2018 基线。原始数据文件可保留，回滚不重建整库。
