# Proposal

## Why

项目全部统计基于 2018 年的静态快照（radishT/Job_Analysis 的 BOSS直聘数据），距今已七年，薪资与技能结构的结论早已过时。项目本身不采集数据，"数据截止日期"由数据集快照决定；要让数据更接近当下，必须引入新一期数据，而现有架构（整库 TRUNCATE + 覆盖式写入、无期次维度）只容得下单快照——重导新数据就会抹掉 2018 期。因此本次先建多期共存的地基，并接入第二期数据集。

## What Changes

- 引入快照（snapshot）维度：新增 `snapshots` 元数据表（期次标签、来源标注、覆盖范围说明），`jobs` / `job_skills` 增加 `snapshot_id` 列；同一岗位跨期存在是合法状态，不再全局去重
- 接入第二期数据集：jhcoco/bosszp 的 2021 年 BOSS直聘 CSV（数据类岗位），作为与 2018 期并存的快照入库；该数据集不含技能列，2021 期无技能数据
- ETL 按快照运行：指定期次执行，重导某期只清除并重建该期数据，其他期不动；去重范围从整库改为快照内；技能摄入按数据来源分路（2018 = Java blob 解码路径保留）
- 查询层增加期次筛选维度：与城市/学历/经验并列为第四维；未指定期次时默认取最新一期，绝不混合多期计算统计
- 页面筛选条增加期次下拉；技能页对无技能数据的期次显示降级提示
- 页脚数据来源标注从全局固定文案改为按当前选中期次动态展示（来源、时间范围、覆盖说明）

**不做**（明确出范围）：跨期趋势对比页面/图表（如 2018 vs 2021 技能变迁）——留待后续独立 change；接入 2024/2025 更新数据集——多期架构建成后，加第三期是纯数据接入工作。

## Capabilities

### New Capabilities

（无——快照维度是数据管道、分析口径、页面呈现三个现有能力的规格级演进，不构成独立新能力）

### Modified Capabilities

- `data-pipeline`: 新增快照元数据与期次隔离要求（多期共存、按快照摄入、跨来源摄入路径）；"去重"从整库语义改为快照内语义；"幂等入库"从整库一致改为批内一致；"必填字段校验"按各快照的数据集各自声明
- `recruitment-analytics`: "筛选条件语义"增加期次维度（默认最新期、不混合多期）；技能统计（词频/共现/词云）增加按期隔离要求——技能行的岗位标识只在快照内唯一，跨期必须隔离统计
- `web-dashboard`: "筛选联动"增加期次控件；"数据来源标注"从固定配置改为按当前期次动态展示；"页面结构"增加技能数据缺失时的降级显示要求

## Impact

- **代码**：`etl/run_etl.py`（按快照运行、DELETE WHERE 替代 TRUNCATE、快照注册）、`etl/cleaning.py`（经验归并补"在校/应届 → 应届生"规则）、`etl/skills.py`（定位为 2018 期专用路径）、`queries.py`（`_where` 加期次、筛选选项按期获取、技能三查询加期次过滤）、`app.py`（期次参数与默认最新期、页脚动态注入）、`config.py`（`DATA_SOURCE`/`DATA_PERIOD` 退役为兜底或移除）、全部模板（筛选条、技能页降级、页脚）、全部测试
- **数据**：`data/README.md` 增补 bosszp CSV 的获取路径；存量 `jobs`/`job_skills` 行回填 2018 期标识（或重跑 2018 期 ETL 重建）
- **依赖**：无新增第三方依赖（CSV 读取用 pandas 现成能力）
- **兼容性**：数据库表结构变更（加列 + 新表），本地单机项目无外部消费者；旧的全量统计行为被"默认最新期"取代，属有意变更
